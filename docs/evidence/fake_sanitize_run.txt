WHERE THE FLOOR COMES FROM — it is derived, never a constant
------------------------------------------------------------
  baseline source            observed_pass
  baseline measured          True
  probe bytes                268,435,456
  probe elapsed              431,059,458 ns
  measured write rate        622,734,175 B/s
  work claimed               268,435,456 bytes

  expected_min = work_bytes * probe_elapsed_ns / probe_bytes
               = 268,435,456 * 431,059,458 / 268,435,456
               = 431,059,458 ns

  Computed in u128 integer arithmetic, truncating downward so rounding always
  favours the device. A hardcoded floor would false-positive on fast NVMe; this
  one moves with whatever the medium actually demonstrates.

A SECOND, INDEPENDENT SIGNAL
----------------------------
  Timing is not the only witness. The medium itself is sampled before and after:
    medium_witness_before    c82e10f39199bc4fb1728f8bf12f3049717809b47956437d3f549917b57fc9c6
    medium_witness_after     c82e10f39199bc4fb1728f8bf12f3049717809b47956437d3f549917b57fc9c6
    medium_unchanged         True   (over 256 sampled sectors)
  So the claim is corroborated twice: the command was impossibly fast, AND the
  bytes it claimed to erase are unchanged.

  disposition                NOT_A_SANITIZATION_CLAIM: the primitive is not claimed by this device, so the command was simulated. The overwrite behind it is what this report's sanitization claim rests on.

WHAT THIS DOES AND DOES NOT PROVE
---------------------------------
  It rules out the specific failure where a firmware command returns success
  without doing the work, independently of anything the firmware reports.
  It does NOT prove an erase happened when timing looks plausible: a device that
  fakes host writes fast enough would inflate the measured baseline and disarm
  this audit. Only read-back verification addresses that, and it is a separate
  and necessary check. Every figure here is host file I/O on one laptop; no real
  ATA or NVMe device has been timed.
