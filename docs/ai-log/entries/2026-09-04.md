## 14:30 · The live run signs and chains

**Asked.** Point `ui/serve.py` at the new `verify` binary so a live run produces
a real certificate, not just numbers.

**Produced.** `serve.py`'s runner no longer drives three binaries by argv; it
calls `verify` once. That is not a tidy-up: `verify` enforces parameter identity

by tailing the trace while the process runs. A new `ledger` event carries
`signed_certificate`, `chain`, and `certificate_canonical` produced by the same

hashes exactly the bytes the engine signed.

screen: the live run's if there was one, the recorded run's otherwise, and the
card says which. Verified in Chrome — before a run the card shows the recorded
digest `931e8462…`; after a live run it shows that run's own, with a different
public key and signature, and forging `whole_medium_claim` inside the canonical
bytes makes the digests part company and prints SIGNATURE INVALID while the
chain head still proves the original.

Measured live: carve 2.99 s (server clock), wipe 1.6108227 s (the engine's own
figure), second carve 2.72 s, whole loop 7.32 s, ~130 frames streamed, zero
console errors, zero requests off 127.0.0.1.

Two real bugs found by instrumenting the phases rather than trusting them.
The trace tail runs until the PROCESS exits, not until the wipe ends, so the

1. **The carve phases have no engine timing.** The carve reports carry no

2. **`serve.py` is not covered by any test.** It was exercised by hand and by a

## 17:40 — live recovery from a real USB stick

**Task.** "Is it possible to show a live demo of deleting a file from my USB and
getting it back?" Yes, and it now works on real hardware.

**Shape.** Enrol, then image, then carve, then join by SHA-256.
`ui/usb.py` walks the mounted volume and hashes every file BEFORE anything is
deleted — that enrolment is the only reason a recovered object can be called
correct rather than merely plausible. The operator then deletes in Explorer,
outside this tool. The volume is imaged read-only into a file, the shipped
carver runs against that FILE, and each recovered record is joined to the
enrolment by SHA-256 alone: not by name, not by size, not by offset.

Imaging first is not a workaround for `carve` taking a file. It is the order a
forensic examiner works in — you work on a copy — and the image's own SHA-256 is
recorded so the copy can be shown to be a copy.

**Read-only, without exception.** Every handle `ui/usb.py` opens on a volume is
opened `"rb"`. There is no write path in the file. `_require_removable` refuses
any drive Windows does not report as removable, so the operator's system disk
cannot be imaged even by typo. The wipe half stays on the loopback image: this
product recovers from a device somebody brought with them, it never erases one.

**Measured, on a real 62 GB exFAT stick.** Eight files staged — one of every
kind the carver knows, plus a `.txt` we predicted would fail. Imaged
269,484,032 bytes in 14.97 s at ~30 MB/s, carved in 3.26 s, 857 candidates and
725 admitted. **Seven of eight recovered byte-exact, all seven above the
confidence gate.** The eighth was the `.txt`, exactly as predicted before the
run — plaintext has no header to scan for.

**The scope limit is reported, not hidden.** A 62 GB volume at USB 2.0 speed is
forty-four minutes of imaging, which is not a demonstration, so the read is
bounded to the used region plus headroom. Anything past that point was NEVER
READ and is reported as out of scope rather than as unrecoverable — the same
discipline `whole_medium_claim` follows, for the same reason. `compare()` checks
the scope BEFORE the signature table, so a partial image can never let us blame
the carver for bytes it was not shown.

3. **The raw read needed no elevation here.** `\.\D:` opened read-only without

## 18:30 — recovery writes files, and the over-run boundary is named

**Task.** "Shouldn't the files be recovered onto my USB again? Currently it only
shows on the frontend." A fair complaint against a real gap: the tool compared
hashes and wrote nothing.

**Files now come back as files.** `extract()` cuts each recovered object out of

**Never back onto the source, and the code enforces it.** `extract()` refuses a
destination whose drive letter is the volume that was just imaged. Writing
recovered data onto the medium you are recovering from can overwrite the very

impossible, and the page says so on its face rather than leaving it as folklore.

## 19:15 — put them back on the stick

**Task.** "Put it back in the USB, it's a demo to look cool." I had refused to
write to the source volume. Re-examined and the objection was wrong AS APPLIED.

**Why the earlier refusal was over-broad.** The rule is that you never write to
a medium while you still need to READ from it — a write can land on bytes not
yet carved. By the time a restore would run, the volume is already imaged, the
image is already carved, and every recovered object is already on local disk and
hashed. There is nothing left on the stick to lose, and the image on disk means
the whole run repeats without the device. **The ORDER is the safety property,
not a prohibition**, and `restore()` now enforces that order rather than
banning the operation: it refuses unless the extraction it is asked to copy
already exists on local disk.

**The read-back is the claim, not the copy.** Files are written to
`D:\RECOVERED`, then read BACK OFF the volume and hashed there. A file is
reported restored only if the bytes now on the stick hash to what was enrolled
before the deletion. A write that was not read back is a hope.

**Measured end to end, one browser run:** 8 files staged, enrolled, deleted;
269,484,032 bytes imaged in 8.68 s; carved in 3.28 s, 854 candidates, 725
admitted; 7 of 8 recovered; 7 written to local disk and verified; **7 of 7
written back to D: and re-read there, all identical to the original**. Confirmed
independently by hashing straight off the USB. The eighth is the `.txt`.

**Three defects found and fixed on the way.**

1. `extract()` and `restore()` appended `(1)`, `(2)` copies across runs instead
   of describing one run, so a later restore copied a stale object the current
   enrolment had never heard of — and honestly reported it as having no ground
   truth, which is how it was noticed. Both now clear their own output first.
2. **Two stale `serve.py` processes were sharing port 8787.** Windows permits
   it, so a killed-and-restarted server kept being answered by old code with old
   `usb.py` imported — which is why a route returned 404 and a fixed bug looked
   unfixed. Killing by PID from `netstat -a -n -o` is the reliable way; a
   `taskkill` on the image name is not.
3. `shutil.copy2` fails on exFAT in `copystat`. Test helpers use `copyfile`.

**Unsure.** Two things.

1. **`restore()` writes to the operator's device.** It is gated on the order and
   on the volume being removable, and it only ever creates `\RECOVERED`, but it
   is still the first write path in this module and the module's own docstring
   had to be rewritten from "read only, without exception".
2. **The PDF over-run is still a real carver defect**, unfixed in
   `core/carve/src/structure/pdf.rs`. It reproduces whenever two PDFs land
   adjacent, and this run showed it again.

## 21:05 — where recovery actually stops, measured rather than assumed

**Task.** "What is the max file size it can recover, so I don't overstate?"

**The honest position before this.** The fixture's largest planted object is
260,595 bytes, so every claim about anything larger was untested. The engine's
own tables imply much higher ceilings, but a table is not a measurement.

**So it was measured.** Three genuinely large valid files were built with the
fixture's own generator — a 5,170,540 byte JPEG, a 5,570,157 byte PNG and a
13,277,809 byte PDF — copied to the real stick alongside two small controls,
deleted, and recovered.

**5 of 5 byte-exact, every one at confidence 1.0000.** Imaged 269,484,032 bytes
in 8.71 s, carved in 6.20 s, 847 candidates and 722 admitted. The largest object
recovered byte-exact is now **13,277,809 bytes**, up from 260,595 — a 51× jump
in what is actually demonstrated.

**The real ceilings, in the order they bite.**

1. `Signature::max_len` is the hard clamp — the carver will not search past it
   from a header: JPEG 32 MiB, PNG 64 MiB, PDF 64 MiB, ZIP/DOCX 128 MiB,
   SQLite 256 MiB, MP4 256 MiB, GZIP 128 MiB.
2. `size_plausibility` degrades above `full_hi` and reaches zero at `zero_hi` —
   but it carries weight 0.10, so a perfect object with ZERO size credit still
   scores 0.90 against a 0.75 gate. **Size alone cannot sink a recovery**, which
   is worth knowing before anyone claims it as a limit.
3. Fragmentation is the limit that actually matters for large files, and it is
   not about size: a big file on a full volume is far more likely to be split,
   two-fragment reassembly is off by default, and three or more fragments are
   not handled at all.
4. `extract()` and `compare()` read the whole image into memory. Fine at 269 MB,
   a problem at multi-gigabyte scale.

**Unsure.** Two things.

1. **Nothing between 13.3 MB and the per-kind clamps has been tested.** The
   32–256 MiB figures are the code's own bounds, not results.
2. **The large files landed contiguous** because the stick was nearly empty.
   That is the favourable case, and it is exactly the case a fragmented volume
   would not give.
